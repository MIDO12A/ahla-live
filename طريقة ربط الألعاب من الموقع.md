## 2) Overview

```
App  ── opens the game URL with player parameters ──►  Game website
App  ◄── reads the balance from the database ────────  Database
Game website  ── callback to server ──►  Your server  ── updates player balance ──►  Database
```

The app opens the game with the player's parameters. After each round, the game calls your server. Your server updates the player's balance in the database.

---

## 3) Server setup

Expose three POST endpoints under `<CALLBACK_BASE_URL>`:

| Endpoint | Purpose |
|---|---|
| `/get-user-info` | Return player data and balance before the round |
| `/change-balance` | Settle a bet or a win |
| `/make-up-orders` | Re-settle a missing order |

### 3.1 Signature

```
md5(fields concatenated with no separators + APP_KEY)
```

- Calculated in lowercase.
- Sent in `body.sign` or in the query string.
- Compared case-insensitively.

| Endpoint | Signature formula |
|---|---|
| `/get-user-info` | `md5(gameId + uid + token + roomId + APP_KEY)` |
| `/change-balance` | `md5(orderId + gameId + roundId + uid + coin + type + rewardType + token + winId + roomId + APP_KEY)` |
| `/make-up-orders` | `md5(orderId + gameId + roundId + uid + coin + rewardType + winId + roomId + APP_KEY)` |

### 3.2 Response format

HTTP is always 200.

```json
{ "errorCode": 0, "errorMsg": "success", "code": 200, "msg": "success", "data": {} }
{ "errorCode": 10004, "errorMsg": "Verify signature fail", "code": 10004, "msg": "Verify signature fail", "data": [] }
```

| Code | Meaning |
|---|---|
| 10001 | Missing fields |
| 10002 | User not found |
| 10003 | Insufficient balance |
| 10004 | Bad signature |
| 10005 | Settlement failed |
| 10006 | Settlement secret not set |
| 10007 | Ambiguous settlement direction |
| 10099 | Internal error |

### 3.3 Player data — `/get-user-info`

Request:
```json
{ "gameId": "<GAME_ID>", "uid": "<UID>", "token": "<TOKEN>", "roomId": "<ROOM_ID>", "sign": "<MD5>" }
```

Response:
```json
{
  "errorCode": 0,
  "data": {
    "uid": "<UID>",
    "nickname": "<NAME>",
    "coins": 0,
    "coin": 0,
    "balance": 0,
    "avatar": "<AVATAR_URL>"
  }
}
```

### 3.4 Settlement — `/change-balance`

Request:
```json
{
  "orderId": "<ORDER_ID>",
  "gameId": "<GAME_ID>",
  "roundId": "<ROUND_ID>",
  "uid": "<UID>",
  "coin": 0,
  "type": "2",
  "rewardType": "<REWARD_TYPE>",
  "token": "<TOKEN>",
  "winId": "<WIN_ID>",
  "roomId": "<ROOM_ID>",
  "sign": "<MD5>"
}
```

Settlement rule:

| Event | `type` | Action |
|---|---|---|
| Bet | `1` | No balance change |
| Win | `2` | Add `coin` to the player's balance |

- The `coin` sent by the provider is already multiplied by the win multiplier (e.g. bet 1000 × x5 = 5000).
- Credit `coin` as received — do not recompute the multiplier and do not deduct the bet.
- Prevent duplicate `orderId` (primary key in the orders table).

Response:
```json
{ "errorCode": 0, "data": { "orderId": "<ORDER_ID>", "net": 0, "coins": 0 } }
```

### 3.5 Make-up orders — `/make-up-orders`

Accepts one order object or an `orders[]` array with the same fields as `/change-balance` except `type` and `token`.

## 4) Launching the game from the app

Open the game in a WebView:

```
https://<PROVIDER_HOST>/play/<APP_KEY>/<GAME_ID>
  ?gameId=<GAME_ID>
  &uid=<UID>
  &token=<PLAYER_TOKEN>
  &roomId=<ROOM_ID>
  &view_mode=<half|full>
  &user_id=<UID>
  &nickname=<NAME>
  &coins=<BALANCE>
  &avatar=<AVATAR_URL>
```

| Parameter | Source |
|---|---|
| `gameId` | Provider game ID |
| `uid` | Player ID |
| `token` | Player session token |
| `roomId` | Room ID (empty outside rooms) |
| `view_mode` | `half` or `full`, per game |
| `coins` | Current player balance |

---

## 5) Refreshing the balance in the app

After every settlement, re-read the player's balance from the database and display it.
